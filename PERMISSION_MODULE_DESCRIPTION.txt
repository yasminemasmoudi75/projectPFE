MODULE PERMISSION - DESCRIPTION DETAILLEE
========================================
Date: 2026-04-03
Projet: Nexus CRM (Backend + Frontend)

1) OBJECTIF
----------
Le module Permission controle:
- La visibilite des modules dans la sidebar (Actif)
- Les actions par module (canAdd, canEdit, canDelt, canValid, CanImp, canPDF)
- Les acces API backend par role/module/action

Source de verite: table SQL Server TabAWProfileAccess.


2) TABLE BASE DE DONNEES UTILISEE
---------------------------------
Table: TabAWProfileAccess
Colonnes fonctionnelles utilisees:
- ProfileUser (role: Admin, Agent, ...)
- CodMod (code module)
- LibMod (nom module)
- Actif (module visible/actif)
- canAdd (creation)
- canEdit (modification)
- canDelt (suppression)
- canValid (validation)
- CanImp (export)
- canPDF (pdf)

Important:
- Aucune nouvelle table n'a ete creee.
- Aucune nouvelle colonne n'a ete ajoutee.
- Les changements ont porte sur les donnees (UPDATE) et la logique de lecture.


3) CHANGEMENTS EFFECTUES DANS LA BASE
--------------------------------------
3.1 Correction principale
- Role: Admin
- Module: CodMod=4 (Module Devis)
- Probleme: Actif etait a 0
- Correction appliquee: Actif passe a 1

SQL applique:
UPDATE TabAWProfileAccess
SET Actif = 1
WHERE ProfileUser = 'Admin' AND CodMod = 4;

3.2 Verification etat final Admin
- Les modules Admin suivants ont ete verifies en Actif=true:
  3, 4, 5, 6, 7, 30, 31, 32, 40, 41, 42, 43, 44, 45, 46, 47, 52


4) API PERMISSIONS (BACKEND)
----------------------------
Fichier: src/routes/permissionRoutes.js

Endpoints:
A) GET /api/permissions/my-permissions
- Retourne toutes les permissions du role connecte
- Lit TabAWProfileAccess par ProfileUser
- Reponse renvoyee:
  {
    status: 'success',
    data: {
      userRole,
      totalPermissions,
      activeModules,
      permissions: [
        {
          moduleCode,
          moduleName,
          isActive,
          canCreate,
          canEdit,
          canDelete,
          canValidate,
          canExport,
          canPDF
        }
      ]
    }
  }

B) GET /api/permissions/module/:codMod
- Retourne la permission d'un module unique pour le role connecte

Correction importante faite:
- Les flags SQL peuvent revenir en booleen (true/false) ou numerique (1/0)
- Normalisation appliquee dans le mapping backend:
  value === true || value === 1

Exemple:
isActive: p.Actif === true || p.Actif === 1
canCreate: p.canAdd === true || p.canAdd === 1
... etc

Sans cette normalisation, tous les modules pouvaient apparaitre en false cote frontend.


5) MIDDLEWARE D'AUTORISATION (BACKEND)
---------------------------------------
Fichier: src/middleware/checkPermissions.js

Fonction:
- checkPermission(codMod, action)
- Verifie role + module + action avant d'executer la route

Actions supportees:
- create -> canAdd
- read   -> acces module
- update -> canEdit
- delete -> canDelt

Logique notable:
- Lecture des droits dans TabAWProfileAccess
- Gestion des alias de role (admin, administrateur, etc.)
- Lecture autorisee si module accessible (Actif ou flags droits presentes)

Mapping modules (CodMod) principal:
- 4 DEVIS
- 5 BCV / COMMANDES
- 6 LIVRAISONS (BLV)
- 7 FACTURES (FAV)
- 30 CLIENTS
- 31 REGLEMENT
- 32 MENU
- 40 TOURNEE
- 41 CHARGEMENT
- 42 OBJECTIFS
- 43 RECAP
- 44 RELEVE
- 45 VISITES
- 46 STOCK
- 47 SOLDE_CLIENT
- 52 MAPS
- 3 PROJETS


6) FRONTEND - CHARGEMENT DES PERMISSIONS
-----------------------------------------
Fichier: front/src/hooks/usePermission.js

Ce qui a ete corrige:
- Chargement des permissions apres authentification (token present)
- Lecture robuste du payload API
- Normalisation des codes modules en Number

Structure attendue cote frontend:
- response.data.permissions (apres interceptor axios)

Remarque:
- Le hook inclut actuellement des logs debug console.
- Le hook inclut un fallback admin en cas d'erreur API.


7) FRONTEND - SIDEBAR
---------------------
Fichier: front/src/layouts/Sidebar.jsx

Regle appliquee:
- Si moduleCode absent -> item visible
- Si moduleCode present -> visible seulement si permission existe ET isActive === true

Donc:
- Actif=1 en base => module affiche
- Actif=0 en base => module masque


8) FRONTEND - BOUTONS PAR ACTION
--------------------------------
Regle metier appliquee dans les ecrans:
- canCreate=true  => bouton Nouveau/Ajouter visible
- canCreate=false => bouton Nouveau/Ajouter cache
- canEdit=true    => bouton Modifier visible
- canEdit=false   => bouton Modifier cache

Ecrans ou cela a ete applique:
- ClientsList
- ProductsList
- ActivitesList
- DevisList
- BcvList
- BlvList
- FavList
- ProjetsList
- ProjetDetail
- Objectifs


9) SCRIPT DE TEST BASE DE DONNEES
---------------------------------
Fichier utilitaire cree: toggle-module.js
Emplacement: backend/backend/toggle-module.js

Usage:
- node toggle-module.js <codMod>
  (toggle 0/1)
- node toggle-module.js <codMod> 0
  (desactive)
- node toggle-module.js <codMod> 1
  (active)

Exemple:
- node toggle-module.js 4 0   -> desactive Devis pour Admin
- node toggle-module.js 4 1   -> reactive Devis pour Admin


10) CHECKLIST RAPIDE DE DIAGNOSTIC
----------------------------------
Si un module ne s'affiche pas:
1. Verifier TabAWProfileAccess (ProfileUser, CodMod, Actif)
2. Verifier endpoint /api/permissions/my-permissions
3. Verifier que isActive remonte true
4. Verifier mapping CodMod frontend/backend

Si un bouton Nouveau/Modifier ne s'affiche pas:
1. Verifier canAdd/canEdit en base
2. Verifier permissions dans hook usePermission
3. Verifier condition JSX (canCreate && ... / canEdit && ...)
